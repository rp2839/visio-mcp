# Final review: R1–R4 and the integrated corrections

I agree with all four proposed resolutions. R2, R3 and R4 each need a refinement before they're consistent with the rest of the design. I found three new contradictions that block production behaviour, listed in §3; none of them blocks M0. The integrated host corrections are present and I agree with them, with two small additions. I made no edits; every change below is a proposed edit.

## 1. Verdicts

### R1 — Explicit session and document identity on every mutation: **Agree**
I drop my earlier revision-only degraded mode. A shim that silently fills in the last-seen session is exactly how a stale edit lands after a reopen. `architecture.md:91-93` and `host-and-interoperability.md:39-40` already say this.

**Refinement (a spec change):** spec §11.2 lists only `baseRevision`, `operations`/`script` and `atomic` as inputs to `apply_operations` and `execute_script` (spec lines 873–887). Adding required `sessionId`, `documentId` and `transactionId` changes the spec, so it should be a row in QUESTIONS (see edit Q-3). A missing `transactionId` is rejected, not generated by the shim, because a shim-generated ID would make retries unsafe.

### R2 — Deduplicate by (sessionId, documentId, transactionId): **Agree, with ordering and in-flight refinements**
- **Key:** `(sessionId, documentId, transactionId)`, where `transactionId` is a UUID. No connection ID or client ID is part of the key.
- **Hash:** a canonical hash (RFC 8785-style JSON canonicalisation) over `method`, the scope (`sessionId`, `documentId`, `pageId`), `baseRevision` and the normalised `params`.
  - It excludes `requestId`, deadlines and origin.
  - For `execute_script` it hashes the source text, not the compiled operations, so a compiler change cannot alter the hash.
- **Where the check happens:** at the head of the queue, after session/document validation and before the `baseRevision` check. If it ran before the revision check, a retry after a commit would always fail with `revision_conflict`. Running it at the queue head also makes in-flight duplicates safe: because the queue is FIFO, the original has already committed by the time the duplicate reaches the head. If the check ran at intake, it would miss a duplicate that arrives while the original is still queued. That is contradiction C2 below.
- **What is cached:** only commits and `noChange` results. Validation rejections don't need caching; a retry is simply evaluated again.
- **Unknown ID within the same session:** the host can't tell "never received" from "evicted". It reports the retention floor (lowest still-cached revision), and the client reconciles through `get_changes`, which includes `transactionId`.
- **After a session change** (reopen or renderer crash): only state-based reconciliation is possible, because history isn't carried across sessions (`editor-and-commands.md:119-120`). `host-and-interoperability.md:62` currently says "state/history reconciliation", which promises more than the design delivers.

### R3 — Human-gesture interlock: **Agree, with a per-connection ordering fix**
The proposal is coherent, and the existing stale-gesture rejection stays as a backstop. A mutation that was already admitted to the queue before the gesture started can still commit mid-gesture. The gesture then fails the `baseRevision` recheck, its preview is discarded, and the user sees a status message (`editor-and-commands.md:137-138`; `architecture.md:124-125` remain valid).

Required refinements:
1. **Per-connection order (contradiction C1).** `host-and-interoperability.md:81-82` promises per-connection forward order. A mutation held for up to 3 s outside the queue would be overtaken by a later read from the same connection. Fix: make the admission gate per-connection FIFO, so later requests from that connection wait behind the held mutation. Other connections' reads proceed normally and see the last committed state. The 3 s wait counts toward the 15 s mutation deadline.
2. **What counts as a gesture:** pointer drag, resize, rotate and bend previews, plus an active in-place text edit session (`editor-and-commands.md:140`). Selection, zoom and rubber-band selection don't count.
3. **New error code:** `busy_user_editing`, with `retryable:true` and `outcome:"not_applied"`. It isn't in the code list at `architecture.md:110-115` or `host-and-interoperability.md:41-42`.
4. **Lifecycle barriers** (open, close, recovery, renderer crash) cancel the gesture explicitly before the barrier enters the queue. Undo and redo can't enter during a gesture from the GUI. An MCP undo doesn't exist in this design.

### R4 — Group bounds: **Agree, with one blocking refinement about which geometry is used**
Spec `ElementBase` (spec lines 279–291) gives groups required `bounds` and `rotationDeg`, so both stay in the schema and are constrained:

- **`group.rotationDeg` must be 0.** This is a spec change (row A13). Rotating a group expands to rotating each descendant about a pivot; the group's bounds are then re-derived.
- **`group.bounds` is computed by the engine**, as the tight axis-aligned union of descendants' **canonical** geometry:
  - shapes, text and images: the axis-aligned box of their rotated rectangles;
  - connectors: authored fallback `bounds`, waypoints and free endpoints only. It never uses routed `visualBounds`.

  This is contradiction C3. If group bounds used routes, moving a non-grouped shape that is glued to a grouped connector would change the group's hash. That breaks the "unrelated objects unchanged" test and the A4 promise of stable connector hashes. The routed group frame goes only in the projection sidecar; export uses the sidecar's group visual bounds as the Visio group frame at revision R.
- **The engine writes `group.bounds`; callers can't patch it.** Direct `bounds`/`rotationDeg` patches on a group are rejected (`invalid_request`). The inspector translates its edits into move, resize or rotate operations. A commit checks the stored value for exact equality with the same deterministic function. The 0.01 pt tolerance applies only to native comparisons.
- **Any change to a descendant's geometry** marks every ancestor group as changed and reports its ID.
- **Pivot drift.** The centre of the new tight box after a rotation generally isn't the old centre. For example, rotating an L-shaped group by +θ and then −θ ends up translated. So:
  - the rotate operation takes an optional `pivot`, defaulting to the current centre;
  - a GUI rotate gesture computes every step from its start-of-gesture snapshot and pivot, not incrementally.

  Document that sequential group rotations don't necessarily round-trip without an explicit pivot. The inspector shows a group rotation of 0.
- **Resizing a group:**
  - A non-uniform scale is allowed only if every descendant's rotation is a multiple of 90°; at 90° and 270° the axes swap.
  - Otherwise the operation is rejected (`invalid_request`, `details.reason:"nonuniform_group_scale"`), and the GUI resize handle locks the aspect ratio.
  - Stroke widths and font sizes don't scale.
  - Free connector points and waypoints transform with the group; glued endpoints stay derived.
- **Groups with no children are invalid.** Removing the last child requires ungrouping or deleting the group explicitly.
- **Import:**
  - Visio group angle: normalised into descendant transforms. Classified as semantically equivalent, with a diagnostic.
  - Frame margins or a frame looser than the children: tightened. Children's page positions are preserved, with an `approximated` diagnostic.
  - A Visio group's own geometry, text or fill: becomes an explicit child element, or is reported as `dropped`. It is never silent.
  - Group resize behaviour, selection mode and child formulas that refer to the group's size: diagnosed.
- **Export** writes children in group-local coordinates with constant values. M0 should check what happens when a user resizes the exported group in Visio; this is an evidence item, not a blocker.

## 3. Blocking contradictions found in this pass
- **C1 — R3 interlock versus per-connection order.** `host-and-interoperability.md:81-82` promises per-connection forward order, which a held mutation would break. Fix: the per-connection FIFO admission gate in R3 refinement 1.
- **C2 — R2 versus the transaction lifecycle.** `editor-and-commands.md:93` runs the cache check at step 1 (intake), before session validation. It must run at the queue head, between session/document validation and the `baseRevision` check.
- **C3 — R4 versus stable connector hashes.** If group bounds include routed connector geometry, they change as a side effect of moves that don't touch the group. Fix: derive group bounds from canonical geometry only (R4).
- **Wording conflict.** `host-and-interoperability.md:88-89` names stale-gesture rejection as the selected policy, which contradicts the agreed R3.
